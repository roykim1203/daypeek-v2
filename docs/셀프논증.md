## 쟁점 1 — 모든 일정을 표시할 것인가, `+N개`로 숨겨진 일정 수를 알릴 것인가?

**작성자 주장** (작성자, prompt-log 2 · 15)
월간 달력에서는 모든 일정 제목을 무리하게 표시하기보다 **숨겨진 일정의 정확한 개수를 알려 주는 것**이 중요하다. 규칙: 5개 중 3개가 보이면 `+2개`, 2개가 보이면 `+3개`, 모두 보이면 배지 없음.

**AI 반론** — [문서 단계 AI 반론] (개발 중 이 쟁점에 대한 반론 기록은 없음)
1. `+N개` 배지는 숨겨진 일정의 **내용**을 직접 보여 주지 못한다 — "3개가 더 있다"는 알아도 무엇인지는 모른다(P06 재인 약화).
2. 작은 날짜 칸에 배지를 하나 더 넣으면 칸이 복잡해진다(P08 미니멀 위배).

**작성자 재반론 및 수정**
- [실제 반영 기록]
  - 배지 줄 높이를 **먼저 확보**하고 남은 공간에 들어가는 일정만 그림 → 배지가 일정 제목과 겹치거나 잘리지 않음 (`visibleScheduleCount`, prompt-log 2 · 3).
  - 일정이 모두 보이는 날은 배지를 그리지 않음.
  - 배지 · 날짜 칸을 누르면 같은 날짜의 하루 일정 패널(B)로 이동해 **전체 일정을 시간순으로** 봄 (prompt-log 4).
  - 배지는 흰 바탕 + 테두리 + `›`로, 색을 채운 일정 막대와 모양을 구분 (prompt-log 6).
- **작성자 재반론** [작성자 최종 의견 — 셀프 논증 단계]
  월간 달력에서 모든 일정 제목을 표시하려면 글자가 작아지거나 화면이 복잡해질 수 있다. 내가 해결하고자 한 핵심 문제는 일정이 일부 숨겨졌다는 **사실조차** 사용자가 명확히 알기 어렵다는 점이다. 따라서 보이는 일정은 그대로 보여 주고, 나머지 개수는 `+N개`로 알린 뒤 날짜를 누르면 전체 일정을 확인할 수 있도록 하는 것이 더 적절하다고 판단하였다.

**최종 결정**: **유지** — 보완(배지 자리 확보 · 배지/날짜 탭 → 전체 패널).

**Nielsen 원칙**: P01 시스템 상태의 가시성(숨은 일정의 존재 · 개수) · P06 기억보다 재인(날짜를 하나씩 눌러 기억하지 않아도 됨) · P08 미학적 · 미니멀(다 보이는 날은 배지 없음, 숫자 · 막대 · 배지 외 장식 없음)

**실제 리뷰 · 테스트 · 코드 근거**
- 실제 리뷰 R5(Google Play ★5, 2026-06-21, 작성자 이름 지움, [공개용 캡처](screenshots/public/review4_public.png)): "하루 일정표가 4개를 넘어가면 날짜를 눌러서 확인하기 전까지는 모르겠더라고요 … 옆에 작게 +2 이런식으로라도 알려주면 훨씬 편할 것 같아요" · R2(★5, 2026-09-18): "같은날에 여러 일정이 있을 때 한개만 표시됩니다"
- 사례 A(직접 테스트 기록): 5개 중 2~3개만 보이고 숨은 개수 안내 없음, 날짜를 선택하면 5개 · 사례 B(캡처): 6개 중 월간 칸 3개, 숫자 안내 없음, 날짜 선택 후 6개

## 쟁점 2 — 글자 크기가 커져도 가독성과 정보 접근성을 어떻게 유지할 것인가?

> 쟁점 1이 "숨은 수를 알릴지"라면, 이 쟁점은 **글자 크기가 바뀔 때** 읽기 쉬움과 정보에 닿는 길을 어떻게 지키는지에 집중합니다.

**작성자 주장** (작성자, prompt-log 15)
글자 크기를 키우는 사용자에게 **작은 글씨를 강요해서는 안 된다**.

**AI 반론** — [문서 단계 AI 반론] (개발 중 이 쟁점에 대한 반론 기록은 없음)
1. 글자가 커지면 **날짜 칸 높이를 늘려** 모든 일정을 넣으면 된다.
2. 또는 월간 화면의 **일정 글자만 작게 고정**하면 몇 개든 들어간다.

**작성자 재반론 및 수정**
- [실제 반영 기록]
  - 보이는 일정 수를 정할 때 **실제 글자 크기(`textScaler`)로 한 줄 높이를 잼**(`_lineHeight`) → 글자가 커지면 들어가는 제목 수는 줄지만 `+N개`가 그만큼 커져 숨은 수를 항상 알 수 있음.
  - 일정 글씨는 고정 · 축소하지 않고 시스템 글자 크기와 A-9 '글자 크기 미리보기'(DayPeek 자체 3단계 '작게' 0.85 · '보통' 1.0 · '크게' 1.15, 저장 안 함)를 그대로 따름 (prompt-log 3). A 리디자인에서는 일정 글씨를 11sp → 12.5sp로 **키움** (prompt-log 6).
  - 큰 글씨 테스트(320dp · 시스템 글자 1.3배)가 날짜 칸 1px 넘침 버그를 실제로 찾아냈고, 테두리 두께를 계산에 넣어 수정 (prompt-log 4).
  - B · C 화면도 글자 크기에 맞춰 늘어남: B 시간 칸 너비 · 등록자 원 · 브리핑 '오전' 칸이 글자 크기에 비례, C 시트는 길어지면 시트 안에서 스크롤.
- **작성자 재반론** [작성자 최종 의견 — 셀프 논증 단계]
  글자를 크게 설정한 사용자에게 모든 일정을 보여 주기 위해 다시 글자를 줄이라고 요구하는 것은 좋은 해결책이 아니라고 생각한다. 화면에 표시할 수 있는 일정 수가 줄어들더라도 숨겨진 일정의 개수를 정확하게 안내하면, 가독성과 정보 접근성을 함께 고려할 수 있다. 다만 실제 화면 크기에 따라 표시되는 개수가 달라질 수 있다는 한계는 인정한다.

**최종 결정**: **유지** — "보이는 제목 수는 공간에 맞게 조절하되, 보이지 않는 일정 수는 `+N개`로 명확히" (보완: 큰 글씨 넘침 버그 수정 · A-9 글자 크기 미리보기).

**Nielsen 원칙**: P07 사용의 유연성과 효율성(사용자마다 다른 글자 크기 허용) · P01 시스템 상태의 가시성(어떤 글자 크기에서도 숨은 수 표시)

**실제 리뷰 · 테스트 · 코드 근거**
- 사례 A(직접 테스트 기록, 2026-10-28 · 5개): '작게' 3개 → '보통' 2개 · '아주 크게' 2개 · 사례 B(캡처, 2026-10-29 · 6개): [글자가 더 작은 캡처 3개](<screenshots/일정 5개 중 3개가 보이는 모습.jpg>) → [글자가 더 큰 캡처 2개](<screenshots/글자를 키웠을 때 2개만 보이는 모습.jpg>) (설정 이름은 캡처에 없음)

## 쟁점 5 — TimeTree의 익숙한 디자인을 유지할 것인가, 완전히 새로운 디자인으로 바꿀 것인가?

- [문서 단계 AI 반론]
  1. 기존 TimeTree와 너무 비슷하면 v2로서 차별성이 부족하다.
  2. 반대로 지나치게 새로운 디자인은 기존 사용자에게 낯설다.
- [개발 중 실제 반론] (AI → 작성자 요구, prompt-log 6)
  3. 빈 공간을 없애려고 칸 높이를 "남은 높이 ÷ 그달 주 수(5)"로 채우고 글씨를 키우면, 400×800에서 28일 칸에 4개가 들어가 `+1개`가 되어 기존 테스트 조건(`+3개` · `+2개`)이 깨진다.

  - 남은 한계: 칸이 창 높이를 따르므로 아주 높은 창에서는 `+N`이 작아질 수 있음(계산은 실제 공간 기준이라 정확).

## 부록 — AI 코드 제안에 대한 비판적 검증

### 정규표현식으로 JSON 데이터를 수정할 것인가, 안전한 JSON 파싱을 쓸 것인가

- **AI 제안** [개발 중 실제] (prompt-log 8): `mock_server/db.json`에서 `, "aiSummary": "…"` 문자열을 정규표현식으로 지운다.
- **작성자 반론** [개발 중 실제] (prompt-log 8 · 9): 해당 명령 실행을 **거부**. 삭제 전에 파일을 백업하고, 정규표현식으로 문자열을 직접 지우기보다 **JSON 구조를 파싱해서 그 필드만** 제거할 것. 날짜 · 제목 · 시간 · 장소 · 작성자 · 일정별 메모 유지, JSON 유효성과 2026-10-28 일정 5개(DayPeek 시연 데이터) 검사.
- **수정** [실제 반영 기록] (prompt-log 9): Node 스크립트 — 원본 백업(`build/backup/db.before-briefing.json`) → 파싱 → `aiSummary` 키만 삭제 → 다시 읽어 원본과 필드별 비교. 출력: "aiSummary 제거 19개 · 일정 19개 · 메모 3개", "검사 통과: aiSummary 외 모든 필드가 원본과 같음", 2026-10-28 5개.
- **최종 결정**: **수정** — AI 방식 폐기, 작성자 방식 채택.
- **배운 점** [작성자 최종 의견 — 셀프 논증 단계]
  AI가 제안한 방법이 실행 가능하다고 해서 항상 안전한 것은 아니라는 점을 배웠다. 특히 JSON 데이터를 수정할 때는 문자열을 직접 삭제하기보다, 원본을 백업하고 구조를 파싱하여 필요한 필드만 제거한 뒤 결과를 검증하는 과정이 중요하다고 판단하였다.
